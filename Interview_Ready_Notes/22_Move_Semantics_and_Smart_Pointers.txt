=================================================================
📘 C++ MOVE SEMANTICS & SMART POINTERS
=================================================================

    🔹 1 — INTRODUCTION: WHY SMART POINTERS?
    -------------------------------------------------------------
        Problem with Raw Pointers:
            • No automatic cleanup mechanism.
            • Early function exit prevents delete (leaks).
            • Exception thrown before delete (leaks).

        Smart Pointer Solution:
            • Composition class that owns a pointer.
            • Destructor automatically deletes managed memory.
            • Guaranteed cleanup when object goes out of scope.

        Why Move Semantics (Not Copy)?
            Shallow Copy Issues:
                • Multiple smart pointers → same resource.
                • All try to delete → double-free crash.

            Deep Copy Problems:
                • May be impossible (file handles, sockets, mutexes).
                • Extremely expensive (large containers, images).
                • Breaks semantics (unique ownership should stay unique).

            ✅ Move semantics transfers ownership safely (avoids copy).

    🔹 2 — RVALUE REFERENCES
    -------------------------------------------------------------
        Lvalue Reference:
            • Binds to modifiable lvalues only.
            • Syntax: int& ref = x;

        Lvalue Reference to Const:
            • Binds to: modifiable lvalues, non-modifiable lvalues, rvalues.
            • Can't modify.
            • Syntax: const int& ref = x;

        Rvalue Reference:
            • Binds to rvalues ONLY.
            • Can modify the rvalue.
            • Syntax: int&& ref = 5;

        +-----------------------------+-------------+------------+
        | Reference Type              | Binds to    | Can Modify |
        +-----------------------------+-------------+------------+
        | int&                        | Lvalue      | Yes        |
        | const int&                  | L/Rvalue    | No         |
        | int&&                       | Rvalue      | Yes        |
        | const int&&                 | Rvalue      | No         |
        +-----------------------------+-------------+------------+

        Properties of Rvalue References:
            1. Extend lifetime of rvalue (like const lvalue refs).
            2. Non-const rvalue refs allow modifying the rvalue.

        Function Overloading:
            void func(const int& x);  // Lvalue version
            void func(int&& x);       // Rvalue version (preferred for rvalues)

        ⚠️ Rvalue Reference Variables are Lvalues:
            int&& ref{5};     // ref has type int&&
            func(ref);        // Calls func(const int&), NOT func(int&&)

            • Named variables are ALWAYS lvalues (regardless of type).
            • Type != value category.

        Returning Rvalue References:
            ❌ Almost never return int&&.
            • Returns dangling reference (object destroyed at function end).

    🔹 3 — MOVE CONSTRUCTOR & MOVE ASSIGNMENT
    -------------------------------------------------------------
        Default Behavior:
            • Compiler provides shallow copy ctor and copy assignment.
            • Classes with dynamic memory need deep copy.

        Move Semantics (C++11):
            • Move constructor: Transfer ownership (cheap).
            • Move assignment: Transfer ownership (cheap).

        Syntax:
            ClassName(ClassName&& source) noexcept;          // Move ctor
            ClassName& operator=(ClassName&& rhs) noexcept;  // Move assignment

        ✅ Mark as noexcept (tells compiler no exceptions thrown).

        Implementation:
            • Shallow copy pointer from source.
            • Set source pointer to nullptr.

        When Called?
            Move:
                • Argument is rvalue (literal, temporary, std::move).

            Copy:
                • Argument is lvalue.
                • Argument is rvalue but move functions undefined.

        Implicit Move Functions:
            Compiler generates implicit move ctor/assignment if:
                • No user-declared copy ctor/assignment.
                • No user-declared move ctor/assignment.
                • No user-declared destructor.

            Memberwise Move Behavior:
                • Members with move → moved.
                • Members without move → copied.
                • ⚠️ Pointers are copied (not moved) unless explicit move defined!

        Key Insight:
            • Lvalue: Must copy (may be used later).
            • Rvalue: Can move (temporary, destroyed anyway).

        Valid State After Move:
            ✅ Moved-from object must be in valid state (for destructor).
            • Usually set pointers to nullptr.

        Automatic Lvalue Return:
            • C++ allows moving lvalue return values (object destroyed anyway).
            • Compiler may elide copy entirely (no copy, no move).

        Deleting Move Functions:
            • Can delete move ctor/assignment (= delete).
            • If copy ctor deleted → no implicit move generated.
            • ✅ Explicitly delete or default move functions.

        Rule of Five:
            If ANY of these defined/deleted → define/delete ALL:
                1. Destructor
                2. Copy constructor
                3. Copy assignment
                4. Move constructor
                5. Move assignment

        Issues with std::swap:
            ⚠️ Don't use std::swap in move ctor/assignment (infinite recursion).
            ✅ Use custom swap (doesn't call move functions).

        Mandatory Copy Elision (C++17):
            • Prvalue directly constructed in place (no copy, no move).
            • Part of language spec (not optimization).

    🔹 4 — STD::MOVE
    -------------------------------------------------------------
        - Casts lvalue to rvalue reference → enables move semantics.
        - #include <utility>

        std::vector<std::string> v;
        std::string str{"hello"};
        v.push_back(std::move(str));  // str moved (now in valid but unspecified state)

        Moved-From Objects:
            State: Valid but unspecified.

            ✅ Can Do:
                • Set/reset value (operator=, clear(), reset()).
                • Test state (empty(), size()).

            ❌ Avoid:
                • Using value (operator[], front()).
                • Depends on implementation.

        Use Cases:
            • Sorting arrays (swap pairs efficiently).
            • Filling containers with lvalues.

        std::move_if_noexcept:
            • Returns movable rvalue if move ctor is noexcept.
            • Otherwise returns copyable lvalue.
            • ✅ Safety: Falls back to copy if move might throw.

    🔹 5 — STD::UNIQUE_PTR
    -------------------------------------------------------------
        - Exclusive ownership smart pointer (C++11).
        - Replaces std::auto_ptr.
        - Properly implements move semantics.

        #include <memory>

        auto ptr = std::make_unique<int>(5);  // Preferred (C++14)
        std::unique_ptr<int> ptr2{new int{10}}; // Alternative

        ✅ Allocate on stack (never dynamically allocate smart pointers).

        Accessing Managed Object:
            *ptr        // Dereference (returns reference)
            ptr->func() // Arrow operator (returns pointer)

            if (ptr) { /* has resource */ }  // Check validity

        Move Semantics:
            auto ptr2 = std::move(ptr);  // Transfer ownership

        Arrays:
            auto arr = std::make_unique<int[]>(10);  // Array support
            ✅ Prefer std::vector, std::array, std::string over smart pointer arrays.

        std::make_unique (C++14):
            ✅ Recommended over new.
            ✅ Exception-safe (C++14+).
            • Fixed in C++17 (function argument evaluation order).

        Exception Safety (Pre-C++17):
            func(std::unique_ptr<T>(new T), throw_func());

            Problem: If throw_func() throws before unique_ptr created → leak.
            Solution: std::make_unique() (atomic creation).

        Returning from Functions:
            ✅ Safe to return by value.
            • C++14: Move semantics.
            • C++17+: Copy elision.

        Passing to Functions:
            Transfer Ownership:
                void func(std::unique_ptr<int> ptr);  // Pass by value
                func(std::move(ptr));

            Use Without Ownership:
                void func(int* ptr);  // Pass raw pointer
                func(ptr.get());      // Get raw pointer

        Misuse:
            ❌ Don't let multiple unique_ptrs manage same resource.
            ❌ Don't manually delete resource (unique_ptr will double-delete).

    🔹 6 — STD::SHARED_PTR
    -------------------------------------------------------------
        - Shared ownership (reference counting).
        - Resource deleted when last shared_ptr destroyed.

        auto ptr1 = std::make_shared<int>(5);
        auto ptr2 = ptr1;  // Copy (both own resource)

        ✅ Always copy from existing shared_ptr (not raw pointer).
        ❌ Don't create two independent shared_ptrs from same raw pointer.

        std::make_shared (C++11):
            ✅ Preferred (single allocation for object + control block).
            ✅ Safer (prevents independent shared_ptrs to same resource).

        Internal Structure (Two Pointers):
            1. Pointer to managed resource.
            2. Pointer to control block (reference count).

        Independent shared_ptrs (Problem):
            int* raw = new int{5};
            std::shared_ptr<int> p1{raw};  // Control block 1
            std::shared_ptr<int> p2{raw};  // Control block 2 (WRONG!)

            • Each thinks it's sole owner → double-delete.

        ✅ Clone via copy assignment (updates control block correctly).

        Converting from unique_ptr:
            auto uptr = std::make_unique<int>(5);
            std::shared_ptr<int> sptr = std::move(uptr);  // ✅ Allowed

            ❌ shared_ptr → unique_ptr not allowed.

        Responsibility Difference:
            • unique_ptr: One owner (destroy that one).
            • shared_ptr: Multiple owners (all must be destroyed).

        Array Support:
            • C++17: ❌ No array support.
            • C++20: ✅ Array support added.

    🔹 7 — STD::WEAK_PTR (CIRCULAR REFERENCES)
    -------------------------------------------------------------
        Circular Reference:
            • Series where each object references next.
            • Last references first → referential loop.

        Problem with shared_ptr:
            • Circular refs prevent ref count from reaching zero.
            • Objects never destroyed → memory leak.

        std::weak_ptr:
            • Observer (not owner).
            • Doesn't increase reference count.
            • Breaks circular dependencies.

        Usage:
            auto sptr = std::make_shared<int>(5);
            std::weak_ptr<int> wptr{sptr};  // Observe, don't own

            if (!wptr.expired()) {          // Check validity
                auto locked = wptr.lock();  // Convert to shared_ptr
                // Use locked
            }

        ❌ Cannot use weak_ptr directly (no operator->).
        ✅ Convert to shared_ptr via lock().

        Avoiding Dangling:
            • expired() returns true if resource destroyed.
            • lock() returns nullptr if expired.

    🔹 8 — BEST PRACTICES
    -------------------------------------------------------------
        ✅ Prefer smart pointers over raw pointers.
        ✅ Use std::make_unique / std::make_shared.
        ✅ Mark move functions noexcept.
        ✅ Return unique_ptr by value (convert to shared_ptr if needed).
        ✅ Pass unique_ptr by value (transfer), or raw pointer (use).
        ✅ Use weak_ptr to break circular dependencies.
        ✅ Check weak_ptr.expired() before lock().
        ✅ Follow Rule of Five if managing resources.
        ❌ Don't dynamically allocate smart pointers.
        ❌ Don't use moved-from object values (valid but unspecified).
        ❌ Don't create multiple shared_ptrs from same raw pointer.
        ❌ Don't use std::swap in move ctor/assignment.
